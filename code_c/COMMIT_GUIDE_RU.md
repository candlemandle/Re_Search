# Что коммитить в ветку C

**Добавьте только папку `code_c/` в корень общего репозитория.** Архив `code_c_upload.zip` содержит именно эту папку, с кодом, тестами, объяснениями и небольшими сохранёнными таблицами/графиками. Сам архив в Git коммитить не нужно.

После объединения проверенных A/B должны существовать `R/code_b_config.R`, `R/forecast_mfbm.R`, `R/rolling_window.R` и `data/processed/dj30_logvol.csv`. Зависимости от них принадлежат коллегам. Не переносите на GitHub всю локальную папку RS: она содержит старые версии, рабочие копии веток, PDF, временные файлы и результаты прошлых запусков.

## Порядок действий

1. В своей рабочей копии репозитория перейдите в вашу ветку C, основанную на актуальной согласованной ветке команды. Если A/B ещё не объединены, добавление C можно закоммитить заранее, а запускать после их объединения.
2. Распакуйте архив так, чтобы получилась `repository/code_c/`, без лишнего уровня `RS/`. Если загружаете через GitHub, сохраните ту же структуру каталогов.
3. Проверьте тесты и маленький запуск из корня репозитория. Затем добавьте только C, проверьте список файлов и сделайте коммит.

```sh
Rscript code_c/scripts/run_tests.R
Rscript code_c/scripts/run_experiments.R smoke all

git add -- code_c
git diff --cached --name-only
git diff --cached --check
git commit -m "Add Code C mfOU forecasting and research experiments"
```

В списке подготовленных к коммиту файлов должны быть только пути, начинающиеся с `code_c/`. Если у вас уже были подготовлены другие изменения, уберите их из подготовки перед этим коммитом обычным способом. Имя ветки и команда отправки зависят от вашего репозитория; здесь они не выдуманы.

Если старая ветка C уже содержит изменения общих файлов, добавление этой папки не отменит прежние коммиты. Для минимального риска используйте новую ветку от актуальной согласованной базы команды и внесите только этот пакет. Если продолжаете старую ветку, проверьте различия всей ветки с базой: старые правки общих файлов тоже участвуют в объединении.

## Что входит

- `R/`, `scripts/`, `tests/` — новый код и проверки.
- `README*.md`, `EXPLAINED_*.md`, `RESULTS_*.md`, `COMMIT_GUIDE_*.md`, `docs/` — русские/английские объяснения и методы.
- `examples/` — небольшие результаты выполненных исследований, с происхождением, ограничениями и проверками. Они удобны для ревью/защиты и не нужны для вычисления новых прогнозов.
- `.gitignore`, `FILE_MANIFEST.csv` — локальные исключения и контроль содержимого пакета. Манифест перечисляет остальные файлы C с SHA-256; сам себя он не хеширует.

Не добавляйте `part A version 2`, `part B version 2`, старые корневые файлы C, `.Rlib`, `tmp/`, полный `results/`, кэш и сырые копии данных. Готовые данные уже предоставляет A/B. C создаёт новые результаты в `results/code_c_v2/`; для этого коммита достаточно `git add -- code_c`, общий `.gitignore` менять не требуется.

## Почему это снижает риск конфликтов

C добавляет новые пути и не меняет файлы A/B, общий README, общий сценарий запуска или их конфигурацию. Совместимость проверена на локальных проверенных версиях, включая расположение A/B в корне проекта. Сравнение с сохранёнными отпечатками подтверждает, что исходные версии коллег не изменены.

Без текущей удалённой истории нельзя гарантировать отсутствие любых конфликтов: если кто-то параллельно добавил собственную папку `code_c/` или изменил интерфейс B, потребуется согласование. Проверка текущих локальных версий покрывает предоставленный код, а не неизвестные будущие коммиты.

В этой папке RS нет `.git`, и адрес репозитория/имя ветки не предоставлены. Поэтому настоящий коммит и отправка не выполнялись. Пакет готов к добавлению в вашу ветку; фиктивная Git-история не создавалась.
