# Часть C: дополнительные эксперименты по прогнозу волатильности

**Задача C — проверить, что ещё можно узнать о точности прогноза, используя работающие A/B.** Главный новый эксперимент сравнивает mfBm из B с настоящей стационарной mfOU. Дополнительно проверяются длина истории, ошибка оценивания параметров и способы выбора дополнительных акций. Улучшение не закладывается в программу: она сохраняет и выигрыш, и проигрыш.

Если терминов слишком много, сначала прочитайте [объяснение без формул](EXPLAINED_RU.md). [Фактические результаты](RESULTS_RU.md) отделены от описания того, что программа умеет запускать. Формулы и ссылки находятся в [методах](docs/METHODS_RU.md).

## Как это связано с частями коллег

В B v2 уже находятся функции A v2. C загружает `R/code_b_config.R` и `source_code_b(root)`, затем прямо вызывает `forecast_mfbm_calendar()`. Это тот же прогноз mfBm, который используют коллеги. C повторно использует их оценки параметров, проверку допустимости корреляций, торговый календарь, критерий покрытия окна и функции потерь.

Новый код расположен только в `code_c/`; функции имеют префикс `c2_`. Он не записывает ничего в папки A/B. Отдельный запуск C не требует изменения их общего сценария запуска. После объединения веток структура будет такой:

```text
repository/
  R/                       # проверенные A/B
  data/processed/           # готовые данные коллег
  scripts/                 # сценарии коллег
  code_c/                  # только наша часть
  results/code_c_v2/        # автоматически создаваемые результаты C
```

Локально загрузчик выбирает `part B version 2`, если такая папка есть. В объединённом репозитории он использует корень проекта. Можно задать другой путь через `--ab-root=...` или `CODE_C_AB_ROOT`. Старая B без интерфейса торгового календаря не подходит: загрузчик завершится с объяснением.

## Какие вопросы решаются

| Запуск | Вопрос | Основные результаты |
|---|---|---|
| `mfou` | Помогает ли mfOU по сравнению с mfBm на одинаковых данных? | MSFE, RMSFE, QLIKE, процент изменения потерь, накопленные потери, параметры и сбои |
| Чувствительность в `mfou` | Меняется ли вывод при 250/500/1000 днях истории? | Сравнение окон по пересечению дат, без подмены различий выборки улучшением |
| `simulation` | Как влияют истинная модель и необходимость оценивать параметры? | Известные/оценённые параметры, парные разности потерь и MCSE, bias/RMSE оценок |
| `selection` | Помогает ли другой выбор дополнительных акций? | Фиксированный набор, корреляция, корреляция × H-gap; fBm и HAR как ориентиры |

MfOU предложена в разделе 6 статьи. Известные/оценённые параметры развивают идею таблицы 11. Окна 250/1000 предусмотрены исследовательским заданием. Балл `abs(rho) * abs(H_target-H_asset)` мотивирован теорией статьи, но не доказан как оптимальный. Все основания и пределы переноса изложены в методах.

## Данные и единицы

Основной файл: `data/processed/dj30_logvol.csv` внутри выбранного проекта A/B. Здесь одна строка на торговый день, колонка `date` в формате `YYYY-MM-DD`, затем 30 колонок акций с числовым **log RV**; пропуски записаны `NA`. Локальная версия содержит 5019 строк, от 2005-01-05 до 2025-01-14. Исторические коды, например `ALD`, сохраняются как у коллег.

Это логарифм годовой волатильности `qmle_trade`. Возврат в исходные единицы: `RV = exp(log_RV)`; дополнительное возведение в квадрат не применяется. Файл `mag7_logvol.csv` также есть у A/B: 2698 строк и пять доступных рядов AAPL/AMZN/FB/GOOG/MSFT. Эти C-эксперименты используют DJ30. Повторно скачивать данные для запуска C не нужно.

Основное сравнение: цель AAPL, вложенные наборы из AAPL, ALD, AMGN, AXP, BA; 500 строк торгового календаря; горизонты 1, 2, 3, 4, 5, 10, 15, 20 торговых дней. Реальный шаг — `1/252` года. В симуляции шаг `1/250` задан явно и совпадает с её отдельной постановкой.

Пропуски не сжимают время. Допустимость всех активных вложенных наборов определяется по крупнейшему набору отдельно для каждого окна, как в B: наличие активов в день прогноза и покрытие окна не ниже 90%. Отсутствующее целевое значение убирает соответствующий исход совместно. Будущие данные не используются для отбора окна, оценивания или выбора акций.

## Быстрый запуск

Нужен R; проверенная среда использовала R 4.5.3. Рабочие эксперименты используют base R и функции A/B. Для тестов нужен `testthat` (проверено с 3.3.2); установите его обычным способом в своей среде, если его ещё нет. Используйте окружение коллег, если оно уже настроено. C не добавляет зависимости от Quarto, Pandoc или Python.

Все команды ниже выполняются **из корня репозитория**:

```sh
Rscript code_c/scripts/run_tests.R
Rscript code_c/scripts/run_experiments.R smoke all
```

В этой локальной папке путь будет найден автоматически. Явный вариант:

```sh
Rscript code_c/scripts/run_experiments.R smoke all "--ab-root=part B version 2"
```

Сначала посмотрите объём полного запуска без вычисления прогнозов:

```sh
Rscript code_c/scripts/run_experiments.R full mfou --plan
```

Выполненные исследовательские настройки воспроизводятся так:

```sh
# Все наборы, все три окна, заранее заданные даты примерно раз в квартал
Rscript code_c/scripts/run_experiments.R study mfou --study-step=63 --output=results/code_c_v2/study

# Ежедневные прогнозы для одной и двух акций, 2019–2021
Rscript code_c/scripts/run_experiments.R study mfou --dimensions=1,2 --sensitivity=none --study-step=1 --output=results/code_c_v2/dense_study

# 30 независимых повторений для каждого из трёх генераторов
Rscript code_c/scripts/run_experiments.R study simulation --output=results/code_c_v2/study_simulation

# Выбор акций для AAPL, MSFT, JPM на той же квартальной сетке
Rscript code_c/scripts/run_experiments.R study selection --study-step=63 --output=results/code_c_v2/study_selection

# Проверка чувствительности интервалов и численной точности без полного перезапуска
Rscript code_c/scripts/compare_blocks.R results/code_c_v2/dense_study/mfou/empirical_run.rds
Rscript code_c/scripts/verify_numerics.R results/code_c_v2/study/mfou/empirical_run.rds
```

Обычный `study` использует шаг 21 торговый день и даты формирования прогноза 2019-01-02…2021-12-31. `--study-start`, `--study-end`, `--study-step` меняют их явно. `--dimensions=1,2` выбирает вложенные наборы; `--sensitivity=none` отключает дополнительные окна; `--max-origins=1` ограничивает первые даты для технической проверки. В режиме `all` эти изменения дат распространяются и на selection. План показывает полный настроенный календарь до ограничения `--max-origins`.

`smoke` использует три редкие даты и четыре симуляционных повторения: это проверка работы. `full` использует полный настроенный период и 200 повторений; эмпирическая часть может занять несколько дней. Для пяти акций и окна 1000 ковариационная матрица имеет размер до 5000×5000, сама занимает около 191 MiB; консервативная оценка рабочей памяти около 1144 MiB (1.12 GiB). Скорость зависит от машины. Скрипт ограничивает BLAS одним потоком для предсказуемых затрат. Полный ежедневный запуск всех окон здесь не выполнен.

## Продолжение и сохранение результатов

Прогнозы сохраняются по отдельным окнам и датам в `checkpoints/`. Повторите **ту же команду** с тем же каталогом результатов: готовые ячейки будут прочитаны. Изменение данных, конфигурации или исходников R создаёт другой отпечаток и не использует несовместимый кэш. CSV и отчёт появляются после завершения стадии; частичный кэш не следует выдавать за завершённое исследование.

`reanalyze.R` пересчитывает таблицы/графики по сохранённым прогнозам. Для старых запусков C с отдельной допустимостью наборов он применяет общий прошлый календарь B и сначала сохраняет исходный RDS с суффиксом `.original_per_set.rds`. Прогнозы на оставшихся датах не переоцениваются. `analysis_source_identity.csv` показывает версию анализа отдельно от первоначального `source_identity.csv`. Это происхождение данных, а не повторная оценка новой версией всех моделей.

## Как объяснить метрики и пределы выводов

MSFE — средний квадрат ошибки, RMSFE — его корень, QLIKE — `r - log(r) - 1`, где `r = actual/forecast`. Во всех трёх меньше лучше. `gain_pct = 100*(1 - loss_mfOU/loss_mfBm)`: плюс означает преимущество mfOU. Делится отношение средних потерь на одних и тех же исходах, а не усредняются отдельные процентные ошибки.

Ежедневные парные серии допускают блочный bootstrap при достаточном объёме и покрытии. Пропуски остаются на исходных торговых позициях. Интервалы 95%, точечные и исследовательские; нет поправки за множество проверок. Квартальная сетка не получает интервалов. MCSE в симуляциях — ошибка от конечного числа независимых повторений, а не доверительный интервал реального прогноза.

Оцениватель mfOU — собственный упрощённый моментный метод с несколькими стартами. Он не является точной реализацией полного GMM из литературы. Истинные параметры используются только в симуляции. `ln(2)/κ` описывает затухание детерминированного дрейфа, не время уменьшения дробной автокорреляции вдвое. Условная дисперсия прогноза не включает всю ошибку оценки параметров. Сравнение с mfBm одновременно меняет модель, оцениватель и начальное распределение; весь выигрыш нельзя автоматически приписывать mean reversion.

Проверенный A/B принят с ограничениями воспроизведения статьи. C сохраняет эти ограничения; он не переименовывает результат в точное воспроизведение опубликованных чисел. Независимое окончательное принятие C не заявляется.
